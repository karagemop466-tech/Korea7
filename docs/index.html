GEMS Prize: executive summary

Built 2026-11-04 from the files in docs/results/. Static page; nothing here updates itself.

There is no submission file in this repository that should be uploaded. The competition rasters (training_features.tif, labels.tif, sample_submission.tif) are behind a DrivenData login and are absent here, and the nine GEMSDOE hosts are unreachable from the build environment. 1. The answer to the question you asked

Why did h33-h33-2-b2-...-zeros (reported 0.2778) lead the nine sites? Because the metric credits true positives with a max over a 300 m kernel and charges false positives with a sum over every positive pixel. Once you emit a sparse binary map, extra density buys no true-positive credit and is charged in full. Every one of the nine leaders is a sparse, catalogue-anchored, binary map; every method in the wider list that emits a smooth probability field scores 0.02-0.15. The 0.24-0.28 band is not a detection result, it is an emission result: those submissions place few, clean cells where mapped faults are dense.

Can we beat 0.2778? Yes, and the arithmetic says where the headroom is. In our calibrated testbed a weak per-cell evidence field (pixel AUC 0.62-0.65) with a calibrated sparse emitter scores 0.2705 (95% CI half-width 0.0408) against unmapped faults, while catalogue geometry alone scores 0.0146 — a factor of about eighteen. So beating 0.28 is not a placement problem, it is a real-evidence problem. The ceiling for perfectly placing everything visible is 0.5869, which is where the current 0.4413 leader sits: they have better evidence, not a better trick.

What we did not do: claim a score. Everything below is either arithmetic on the published metric or a simulation calibrated to published statistics. No number on this page is an organizer receipt.

Read the first column: a one-pixel band on target scores 1.0000, a three-pixel band scores 0.8333 and a five-pixel band 0.6250 — a 37% loss for "being safe". A band three pixels off target scores exactly 0. This single table explains most of the spread in the whole leaderboard, and it is why the delivered pipeline emits 1-px binary cells and never dilates.

0.0001DTI of a uniform 0.02 background over 201x201 cells with one true fault cell. Dense probability fields are not "slightly worse"; they are fatal.
0.0000DTI of an all-zero submission. A blocked or empty file scores exactly nothing.
0.8333DTI of a 3-px band on target - what NMS-plus-dilation costs you before a single mistake.

5. The experiments behind those statements

Three pre-declared experiments, run in 90.5 seconds. Testbed: synthetic fault networks calibrated to four published numbers — two independent real catalogues agree at DTI 0.796 (ours: 0.7925), a map displaced 14-21 km scores 0.045 (ours: 0.0326), fault density 1.39% (ours: 0.0143), cells within 300 m 8.37% (ours: 0.0778). The calibration matters: it is the reason a simulated DTI can be compared with a leaderboard at all.

Result: a negative for our own innovation. Plain top-k selection (0.7169) beats the coverage-aware Dinkelbach greedy (0.485) by 0.2319. The greedy over-emits: given the same number of cells it does worse than score-ordered dots (0.3971). Thresholding and NMS are far behind and much noisier. The pipeline therefore defaults to the measured winner, and the fancy emitter ships as a documented, tested, losing option. A negative that is measured is worth more than a positive that is asserted.

6. One command, when the data are present

mkdir -p data
# put numeric_features.tif, labels.tif and sample_submission.tif in data/ (DrivenData login)
python -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python scripts/build_submission.py --data data --out out/submission.tif \
    --registry path/to/registry.json      # omit --registry only if you accept "UNKNOWN"
cat out/submission.run.json

The run card states, without ambiguity: gate results, holdout DTI with its CI and evaluator version, withheld positive counts, leakage-canary trips, emitted cell count, file SHA-256, validator output, and the uniqueness verdict. READY_FOR_SELECTOR is the only status that may be carried into a weekly slot, and promotion is still a separate human decision.

End-to-end self-test on synthetic data (proves the code paths, not the science): holdout DTI 0.5232, 95% CI [0.5209, 0.5257], chosen feature set independent, variant means {"independent": 0.5232, "independent_plus_catalogue": 0.0}, 5 folds, withheld positives [2208, 2220, 2219, 2223, 2222] px. Gates: {"format_valid": true, "holdout_beats_zero": true, "no_leakage_canary_trip": true, "uniqueness_pass": false}. Note that the catalogue-inclusive model scores exactly 0.0000 on the holdout: the distance-to-mapped-faults feature is a shortcut that cannot generalise to unseen segments.

7. Where the remaining risk is

  • Gated data. Nothing here has seen the real features or labels. The pipeline is tested end-to-end on synthetic data of the same format; that proves the code, not the geology.
  • Unverifiable sites. The nine GEMSDOE repositories are not publicly visible, so "unique" can only be tested once you supply their rasters as a registry.
  • Unknown evaluator cell set. E3 shows the winner changes with the masking rule; the run card's holdout therefore reports the regime used.
  • Metric provenance. The metric is transcribed from the public problem description and reproduced by two independent public implementations, not from organizer code. See the line-by-line audit.
