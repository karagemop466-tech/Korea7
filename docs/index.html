1. Why did h33-h33-2-b2 on GEMSDOE32 score 0.2778?

Three measured facts, in order of weight.

(a) The organisers do not score the faults you can see. DrivenData staff answered this directly on 16 September: “Pixels corresponding to known USGS/INGENIOUS faults are masked / excluded from evaluation, so they do not count towards penalty terms.” The test set is a set of faults not in the public database, hand-labelled by the sponsor's experts ([problem description](https://www.drivendata.org/competitions/306/competition-doe-gems/page/967/), [thread 11516](https://community.drivendata.org/t/scoring-clarification-are-known-usgs-ingenious-faults-masked-when-scoring-and-are-they-in-the-final-round-label-set/11516)).

(b) The nine focus files are one family, and the champion is its most pruned member. This is not an inference; the dot-set algebra is exact (measured here, `symdiff = 0`):

  • GEMSDOE25 ≡ GEMSDOE30 (identical 44,090 dots);
  • GEMSDOE31 = GEMSDOE25 minus every dot within 1 px of a mapped fault → 40,199 dots, 0.2708;
  • champion = GEMSDOE31 minus every dot within 2 px of a mapped fault → 37,654 dots, 0.2778;
  • GEMSDOE36 = champion plus 1,200 dots → 0.2750 (adding dots cost −0.0028).

(c) The score is monotone in how few dots sit near the catalogue. Measured dot counts inside the 3 px kernel of the catalogue, against the owner-reported score: GEMSDOE27 12,187 → 0.2449; GEMSDOE24 11,938 → 0.2477; GEMSDOE25/30 8,607 → 0.2600; GEMSDOE31 4,716 → 0.2708; GEMSDOE32 2,171 → 0.2778.

So the mechanism is: those dots sit 100–200 m off the mapped traces, on the fault flank. Live, the truth there is a new fault that is usually absent, so each such dot pays a false-positive tax. Removing them costs nothing in credit and raises the score. The pruning stops helping at 2 px: removing the next ring (2–3 px) removes 2,171 dots that are, for some of them, genuine hits, and the score falls. That measured optimum is why 0.2778 is this family's ceiling.

What the highest score is not. The champion's recovery of the visible catalogue is DTI 0.0067 — below a uniform random field of the same size (0.0692) — because it deliberately avoids the catalogue. Any model trained to predict the labels you can see is being optimised in the wrong direction. This is the single most important structural feature of this competition.

2. Estimated score for every submission in scope

The estimator is derived in src/gems/estimate.py. For a binary prediction the metric collapses to DTI = c·K / (0.2·N + 0.8·K) with c the kernel-weighted recall, N the dot count and K the number of withheld truth pixels. K is pinned by one anchor whose mechanism is known: the 5-px lattice 13GEMSDOE_r13-lattice-s5, measured here at exactly 206,895 dots, owner-reported 0.0904 → K = 12,773. 4. Experiments run this session (all numbers measured here)

Instrument: K7-HIDE-RECOVER-1.0

Whole connected fault segments are withheld with a 10 px buffer; the scored domain is the footprint minus the visible faults and their buffer; every arm is emitted at a matched 20,000-dot budget with a 3 px collar removed; scoring is the official pooled DTI with a segment-level bootstrap 95% CI. Because the test surface never sees a fault label, this instrument is unbiased for it — unlike the catalogue-derived registry files, for which this style of holdout is known to anti-correlate with the live board.
